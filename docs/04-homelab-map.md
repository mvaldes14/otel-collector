## The agent-gateway-ClickHouse path

```
pods/nodes on evaXX
   -> agent DaemonSet pod on that node   (hostmetrics, kubeletstats, filelog)
   -> gateway Deployment                 (batching, tail sampling, ClickHouse exporter)
   -> SigNoz ClickHouse                  (otel_metrics_* / signoz_logs / signoz_traces)
```

Things this explains:

- **The scraper allowlist.** The agent's `hostmetrics` receiver names its scrapers
  explicitly (`cpu`, `disk`, `filesystem`, `load`, `memory`, `network` in the Oct
  config). A scraper not listed = metric family silently gone — which is how
  `system.uptime` vanished while load_average kept flowing.
- **Why the agent isn't the place for tail_sampling.** One trace's spans hit six
  different agent pods. Only the gateway sees complete traces.
- **Why chart upgrades touch telemetry.** The agent ConfigMap is generated by the
  SigNoz helm chart; hand-edits there get reverted on reconcile. Durable changes
  go in chart values, in the k8s-apps repo.

## The standalone `ck-collector` (clickhouse namespace)

This is the interesting one for learning — a plain contrib collector you own:

- Same version family as this lab (0.154), so configs transfer
- It exports into the `clickhouse` namespace's own ClickHouse (separate from
  SigNoz's instance — deliberately, for blast-radius reasons recorded in the
  vault-rag notes)
- When you change its config, you're exercising the exact skills this repo teaches

## Experiments to run against the real fleet (read-only)

1. Compare agent vs gateway self-metrics: `kubectl -n signoz port-forward` the
   agent pod's :8888 and scrape `otelcol_exporter_sent_metric_points` — then do
   the same on the gateway. The gateway's numbers ≈ sum of agents'.
2. Find the ClickHouse exporter config in the gateway ConfigMap and map every key
   back to docs/02 (retry, queue, batching).
3. Watch a metric family die live: bump the agent's scraper interval and watch
   `last(TimeUnix)` per family move in the `otel_metrics_gauge` table.
